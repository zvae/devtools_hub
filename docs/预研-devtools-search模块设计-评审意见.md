# 《devtools-search 文件搜索模块设计方案》评审意见

> 评审对象：`预研-devtools-search模块设计.md`（2026-10-29 版）
> 评审日期：2026-10-30
> 结论：**方向正确，结构清晰，可以进入 M0；但有几处问题需要在 M1 前改掉。**

## 一、总体评价

整份方案的工程素养不错。边界划得清楚，非目标写得明确，已经考虑到云占位文件、中文输入法、按根拆分快照、结果上限这些容易漏的细节。附录 A 说明它已经过一轮审查。

剩下的问题大多出在三个地方：

- **平台行为的细节**：macOS 隐私权限、Windows 拔盘、Windows 重启后怎么追上变化。
- **宿主和模块的交互**：窗口模式切换、失焦隐藏和系统对话框冲突。
- **增量更新时的数据一致性**：节点 ID 复用、并发读写、事件位置和快照不同步。

这几处一旦做成就很难回头改，建议优先处理。

---

## 二、优点

1. **分层和依赖方向很清楚。** 主模块只碰入口和快捷键，而且有可检查的约束（`git diff --stat`、`layering.rs`）。
2. **非目标写得具体。** 内容搜索、MCP/HTTP、Quick Look 都明确排除，范围可控。
3. **一开始就是多根结构**，快照按根拆成多个文件。离线根、移除根、单根损坏都能各自处理，不牵连其他根。
4. **数据结构思路对。** 同名文件共享一份名字，结果只存 ID，路径按需拼接，路径排序用单独的 rank 而不是节点 ID 顺序。
5. **风险意识好。** 没有忽略云占位文件、中文输入法组合状态、单字符查询结果过大、Windows 图标清晰度、注释导致分层检查误报这些点。
6. **默认值偏安全。** 只索引主目录，首次打开才加载，网络卷默认跳过，不启动任何网络服务。
7. **验收标准具体可测**，大部分条目都能直接写成测试。

## 三、主要问题

### 🔴 P0：会导致功能出错，或体验明显不可用

#### 1. macOS 隐私权限（TCC）弹窗没有设计（§5.3、§8.2）

- **问题**：方案只考虑了"没有完全磁盘访问权限时显示横幅"。但实际上，只要扫描 `$HOME`，访问 `~/Desktop`、`~/Documents`、`~/Downloads`、iCloud Drive 时，系统都会**主动**弹出授权框；访问外置盘还会再弹"可移除宗卷"的授权框。"不自动弹窗"这一条做不到。
- **另一个坑**：如果应用是 ad-hoc 签名，或者每次构建签名都会变，TCC 的授权会在每次升级后失效，用户要反复授权。
- **建议**：
  - 在首次扫描前加一个引导页，二选一：先引导开完全磁盘访问权限，或者说明接下来会弹出几次系统授权。
  - 确认发布包使用固定的 Developer ID 签名。
  - 被拒绝的目录要计数并显示出来，不能静默跳过。

#### 2. Windows 上监听目录会导致外置盘无法安全弹出（§7.5、§8.3）

- **问题**：`ReadDirectoryChangesW` 会一直打开着目录句柄，扫描线程也会。用户点"安全删除硬件"时会提示"设备正在使用中"。
- **建议**：
  - 用 `RegisterDeviceNotificationW(DBT_DEVTYP_HANDLE)` 订阅 `DBT_DEVICEQUERYREMOVE`，收到后立即关闭该根的 watcher 并取消扫描。
  - macOS 上同理，在 `NSWorkspaceWillUnmountNotification` 时取消正在进行的扫描。
  - 把"外置盘可以正常弹出"加进验收第 5 条。
  - `WM_DEVICECHANGE` 需要一个带消息循环的窗口。建议在模块内单独开一个线程，创建只接收消息的隐藏窗口；文档里要写明，不要借用 eframe 的窗口。

#### 3. Windows 重启后索引怎么保持最新，没有方案（§7.7）

- **问题**：macOS 可以用 `last_event_id` 追回关机期间的变化，Windows 的 `ReadDirectoryChangesW` 做不到。现在的写法下，Windows 每次启动加载的快照都可能已经过期，而且没有任何提示。
- **建议**：
  - 明确写出 Windows 的策略：加载快照后立即可以搜索，后台全量重扫并原子替换，期间状态栏显示"正在校验"。
  - 把 USN Journal 列为 v2 选项（需要管理员权限或常驻服务，这就是 Everything 的做法）。

#### 4. 快照文件名会冲突（§7.6）

- **问题**：`root_key` 优先用卷 UUID。可是同一个卷上可以有多个根（比如 `~` 和 `/opt/work` 都在启动盘上），它们会算出同一个 `root_key`，互相覆盖快照文件。
- **建议**：`root_key = 卷 UUID + 根相对卷挂载点路径的哈希`。
- **同类问题**：设置里存的是绝对路径。macOS 外置盘重名时可能被挂到 `/Volumes/Disk 1`，路径会变。建议根改存为 `(volume_id, 相对卷挂载点的路径)`，绝对路径只作为显示和兜底。`ignore_paths` 也要按同样规则处理。

#### 5. 根目录嵌套或重复没有处理（§7.5）

- **问题**：用户同时添加 `~` 和 `~/work`，会重复扫描、结果出现重复、两个根的 watcher 收到同样的事件。
- **建议**：添加根时检查包含关系。要么拒绝并提示，要么自动把子根在父根里排除掉。

#### 6. 默认根会把模块自己的数据目录也索引进去（§7.6、§7.7）

- **问题**：`data_dir` 在主目录里面（`~/Library/Application Support/...` 或 `AppData`）。每次保存快照都会产生文件事件，搜索结果里也会出现 `.tmp`、`.bin` 这类文件。
- **建议**：始终把 `data_dir/search` 加进内置的不可删除忽略项。

### 🟠 P1：设计有缺口，开工后会返工

#### 7. 窗口模式切换缺少通知宿主的通道（§4.1、§4.4）

状态栏的"固定"按钮和设置页的窗口模式选项都在模块内部改模式，但 `SearchUiOutput` 只有 `request_hide` 一个字段。从 Floating 切到 Pinned 还好（宿主在 `handle_focus` 时会重新读 `hide_on_blur`）。但切到 `Normal`、修改 `decorations`、修改最小尺寸时，宿主都不会去调用 `set_mode`。

**建议**：`SearchUiOutput` 增加 `policy_changed: bool`，或者宿主每帧比较一次 `window_policy()`。

#### 8. 页面切换没有统一的收口（§4.4）

窗口模式恢复、`MinInnerSize` 恢复、`remember_size` 现在只写在 `show_search` 和 `hide_panel` 里。如果用户在 Hub 里直接从搜索页切到剪贴板页，窗口会停在 Normal 模式、最小 800×480、1100×700 的大小。

**建议**：主模块统一走一个 `set_page(from, to)`，离开搜索页时完成所有恢复动作。`shutdown()` 里也要保存一次窗口大小（Pinned/Normal 模式下用户可能从来不隐藏窗口）。

#### 9. Floating 模式下，失焦隐藏会和文件夹选择框冲突（§5.4、§5.5）

点"文件夹"或"添加根目录"时会弹出系统选择框，面板随即失焦，然后自己被隐藏。另外，非激活的 `NSPanel` 托管模态对话框本身也有问题。依赖清单里**也没有文件对话框**（比如 `rfd`），而且 core 层被禁止使用文件对话框。

**建议**：

- 在 `ports` 里加一个 `FolderPicker`，由平台层实现。
- 对话框打开期间暂停失焦隐藏（`SearchUiOutput` 带一个 `suppress_hide_on_blur` 之类的字段）。
- 同时支持把文件夹拖进窗口来添加，作为替代入口。

#### 10. Normal 模式在 v1 的价值有限，还可能让窗口"找不回来"（§5.8）

v1 的 Normal 窗口不在 Dock 或任务栏里，Cmd+Tab 也切不到。被其他窗口盖住之后，唯一的入口是快捷键。可快捷键的逻辑是"窗口可见就隐藏"，所以用户按下去，窗口反而被藏起来了。

**建议**：

- 快捷键逻辑改成"窗口是当前焦点窗口则隐藏，可见但不是焦点则拉到前面"。
- 更进一步，建议 v1 只做 Floating 和 Pinned，Normal 等到做独立视口时一起上。这样可以省掉 M4 里 1–2 天的工作和一半的平台模式切换代码。

#### 11. 增量更新下的节点 ID 生命周期没有定义（§7.1、§7.9、§7.10）

方案没说删除的节点是留一个空洞，还是放进空闲列表复用。如果复用：UI 手里拿着旧结果，请求 `LoadRows` 时，同一个 `ResultId` 可能已经指向另一个文件，界面上就会显示错的文件。

**建议**：

- 节点删除时只打墓碑标记、不立即复用，等下次全量重建或空闲压缩时再回收。
- 每次查询绑定索引的代际号，`LoadRows` 时校验，节点不存在就显示"已删除"。
- 写明"索引变化后会自动重新执行当前查询（带防抖）"。现在只有 `Dirty` 事件，没有说明 UI 收到后怎么做。

#### 12. 并发模型没有定下来（§7.10）

"只读不可变快照（或加读锁）"二选一，会直接影响索引的数据结构设计，必须在 M0 定下来。

**建议**：

- 每个根一把 `RwLock`。搜索持读锁，在 rayon 里并行执行；事件分小批应用，每批持写锁不超过约 5ms；快照序列化时在读锁下复制，或者分段写出。不要做写时复制的完整快照，对 100 万节点来说太贵。
- 使用**专用**线程池，不要用 rayon 的全局池，以免和 Hub 的其他功能抢线程。
- 扫描线程要降低优先级：macOS 用 `QOS_CLASS_UTILITY`，Windows 用 `THREAD_MODE_BACKGROUND_BEGIN`。
- 机械硬盘和网络卷上，扫描并发数默认设为 1，否则并行扫描反而更慢。

#### 13. 元数据什么时候读，前后说法矛盾（§7.1、§7.3、§7.9）

一处说"扫描时尽量读取"，一处说"需要时再补读"。如果按需补读，`size:>1MB` 这类查询在 100 万节点上要触发 100 万次 `stat`，需要秒级时间，p95 30ms 的目标就达不到。

**建议**：扫描时一律读完元数据。Windows 直接用 `DirEntry::metadata()`（`FindNextFileW` 已经带回来了，不要再按路径 `stat` 一次）。macOS 在 M0 就对比 `read_dir + lstat` 和 `getattrlistbulk` 的耗时，不要等到"成为瓶颈后"再换。

#### 14. 快照和 `last_event_id` 不是原子保存的（§7.6、§7.7）

快照每 10 分钟保存一次。如果 `last_event_id` 存在 manifest 里，或者和快照内容不对应，回放事件时会漏掉或重复一部分变化。

**建议**：`last_event_id` 写进**每个根自己的快照文件**，取值为"这份快照已经包含的最后一个事件"，和节点表一起序列化。

#### 15. macOS 文件名的 Unicode 归一化不能是"可选"（§3.5）

HFS+ 和部分来源的文件名是 NFD 形式，输入法输出的是 NFC。中文不受影响，但带重音的拉丁字母、日文浊音（が）、**韩文**都会搜不到。

**建议**：改为必选。名字表在写入时统一归一化成 NFC。不区分大小写的匹配也要说明规则：只处理 ASCII 还是完整的 Unicode 大小写折叠。建议名字表预存一份小写化的文本，以空间换时间。

## 四、需求覆盖和验收补充

需求主干覆盖得比较完整。建议在验收标准里补上这些：

- **资源占用**：100 万条目时，空闲 RSS 增量 ≤ 150MB（§7.2 有这个目标，但验收里没有）；不打开搜索页时，Hub 的启动耗时和内存不变；空闲时 watcher 的 CPU 占用接近 0。
- **首次扫描**：给出一个参考机器上主目录全量扫描的耗时目标。
- **p95 ≤ 30ms 要明确查询集合**：单字符、3 个字符、多词 AND、路径词、`regex:`、`size:`。正则在 100 万个名字上大概率超过 30ms，应该单独设标准。
- 外置盘可以正常安全弹出（见 P0-2）。
- macOS 首次扫描时隐私授权弹窗的流程（见 P0-1）。
- Windows 应用重启后，索引能反映关机期间的文件变化（见 P0-3）。

## 五、计划和风险

- **Windows 放得太靠后。** 现在 M5 才对齐 Windows，可是 P0-2、P0-3 和 `ReadDirectoryChangesW` 缓冲区溢出这些问题都会影响架构。主目录下一次 `npm install`，即使目录被排除了，事件照样会送进来，很容易导致溢出，进而触发整根重建。建议 **M0 就在 Windows 上验证扫描和监听**，M3 两个平台并行做。
- **补充风险**：缓冲区溢出导致整根重建可能频繁发生。应对办法是使用大缓冲区、在专用线程上尽快重新发起读取、对重建做限流（比如一个根 5 分钟内最多重建一次）。
- **工时偏乐观。** 合计 24–34 人天，没有包含两个平台的手工验收、隐私授权流程和外置盘相关的调试，建议预留 30%–50% 的缓冲。

M1 开工前建议先改完以下 6 项。它们都只需要改文档和接口，越早改成本越低：

1. macOS 隐私授权（TCC）引导流程（P0-1）
2. Windows 拔盘时释放目录句柄（P0-2）
3. Windows 启动后的后台校验重扫策略（P0-3）
4. `root_key` 改为"卷 UUID + 相对路径哈希"，根改存卷相对路径（P0-4）
5. 根目录嵌套/重复检测（P0-5）
6. 自动排除模块自身的数据目录（P0-6）
