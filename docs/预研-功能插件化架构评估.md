# 功能插件化架构评估

> 评估「核心模块 + 各功能按插件组织」是否值得做，以及如果做应该按什么顺序。

## 1. 结论摘要

| 方案 | 可行性 | 骨架成本 | 迁移成本 | 判断 |
|---|---|---|---|---|
| 编译期 `trait Feature` + 静态注册表 | **可行** | 300~500 行 | 6 个功能约 1~2 周 | 条件成熟再做，先做前置 |
| dylib 动态加载 / 用户装第三方插件 | **不可行** | — | — | Rust 无稳定 ABI |
| 现状（`Page` enum + `HubApp` 直持字段） | — | 0 | 0 | 6 个功能撑得住 |

**核心判断**：编译期 trait 注册表（**UI 也属于插件**）在技术上完全成立，代价中等且可控。但它有三个前置条件，缺一不可：

1. 平台能力先成为独立 crate——否则 trait 方法体里全是 `crate::platform::x`
2. 配置先分片——否则加功能仍要改核心 `Settings`
3. **设计系统先独立**——否则功能 UI 搬不出 `ui/` 目录

不做这三件就上 trait，等于给紧耦合套一个壳，「插件」一点没独立。

## 2. 术语：两种「插件」必须分开

讨论中容易混成一件事，它们的代价差一个数量级：

| | 编译期 trait 注册表 | dylib 动态加载 |
|---|---|---|
| 实现方式 | `Vec<Box<dyn Feature>>` 或 `&'static [&'static dyn Feature]` | `libloading` 加载 `.dylib` / `.dll` |
| 谁提供实现 | 本项目代码，编译期已知 | 运行时由磁盘上的文件提供 |
| 能否用 egui | 可以，同一个 crate graph | **不行**，`Ui` / `Context` 过不了 FFI |
| ABI 稳定性 | 无要求（同一编译器） | Rust 无稳定 ABI，走 C ABI + 序列化边界 |
| 新增功能需要重新编译 | 是 | 否 |
| 适用场景 | 隔离变更、收敛胶水 | 用户可装第三方扩展（uTools 生态） |

本项目要的是左边这一列。右边那一列是另一个产品形态。

## 3. 现状盘点：哪些已经是天然边界

抽 crate 和做 trait 的难度，取决于「接口是否已经存在」。逐个检查：

| 模块 | 现状 | 距离可抽多远 |
|---|---|---|
| `devtools-clipboard` | 已独立，只依赖 sqlite/serde | 已完成 |
| `devtools-json` | 已独立，只依赖 serde | 已完成 |
| `platform/*/ocr.rs` | `recognize(&RgbaImage) -> Result<Vec<Line>>`，两平台同签名 | **就是天然 trait**，只差提出来 |
| `snip/ocr.rs` | `recognize_tiled` / `to_text` / `Line`，纯输入输出 | 可抽，`Line` 依赖 `egui::Rect` → 改依赖 `epaint` |
| `platform` | `hub` 内部 `mod`，各功能直接调用 | **真正的瓶颈**，子 crate 一行也拿不到 |
| `Settings` | 扁平 struct，20+ 字段序列化成一个 JSON | 加功能必改核心结构，需要分片 |
| `ui/snipper` `ui/pin` `ui/ocr` `ui/panel` | 已按功能分目录 | 变更隔离已实现，不必为此做插件 |

结论：**「改功能只改各自插件」这个收益，目录划分已经给到了**。插件化额外能省的是「新增功能时的那几行胶水」。

## 4. 用户提出的依赖模型：两种依赖要分开

「截图依赖 OCR，OCR 提供标准输入输出」这句话里其实藏着两类完全不同的依赖，处理方式也不同：

| 依赖类型 | 例子 | 实现方式 | 需要框架吗 |
|---|---|---|---|
| **计算能力依赖** | 截图 → `devtools_ocr::recognize_tiled()` | 普通 crate 依赖，直接调函数 | 不需要 |
| **页面跳转依赖** | 贴图「编辑标注」→ 重新打开截屏遮罩 | 注册表 + `FeatureCtx::open()` | 需要一行接口 |
| **数据依赖** | 贴图 → 读 `Store` 里的图片条目 | 共享 `&Store` | 不需要 |

**计算能力依赖是普通 Rust 依赖，插件框架在这里帮不上任何忙**。真正的插件间耦合只发生在「页面跳转」这一层，而当前这样的调用只有 5 处：

| 调用 | 代码位置 |
|---|---|
| 贴图 → 截屏（编辑标注） | `PinRequest::Edit`、`screenshot::PinEdit` |
| 贴图 → OCR | `PinRequest::Ocr` |
| 截屏 → OCR | `AppEvent::OcrDone` |
| 剪贴板 → 贴图 | `AppEvent::PinClipboard` |
| 快捷面板 → JSON / 剪贴板 | `QuickAction` 各变体 |

这 5 处用「按 id 打开功能」的单一入口就能覆盖，不需要通用事件总线。

## 5. UI 独立化：设计系统必须先出去

要求「UI 也是插件的一部分、尽可能独立」。这在编译期插件模型下**可行**，而且障碍比逻辑独立更小——实测数据如下。

设计系统内部零互引（10 个文件、3,132 行，彼此不 `use` 对方）：

| 文件 | 行数 | 用途 |
|---|---|---|
| `liquid_glass` | 636 | 液态玻璃背景 |
| `fonts` | 529 | 字体与 text style |
| `icons` | 456 | 图标绘制 |
| `native_menu` | 380 | 原生右键菜单 |
| `style` | 356 | `Palette`、圆角、间距常量 |
| `code_text` | 227 | 语法高亮样式 |
| `glass` | 224 | 玻璃栏与描边 |
| `widgets` | 187 | 通用控件 |
| `textures` | 71 | 纹理缓存 |
| `menu` | 66 | 菜单项 |

功能 UI 对它们的依赖很薄：

| 功能 | 行数 | 依赖的共享件 | 依赖 `HubApp` |
|---|---|---|---|
| `ui/snipper/` | ~2.8k | `style`（2 处）、`icons`（1 处） | 无 |
| `ui/pin.rs` | 1.0k | 仅 `native_menu` | 无 |
| `ui/ocr.rs` | 1.1k | `fonts`、`icons`、`style`、`widgets` | **有** |
| `ui/panel/` | ~1.4k | `native_menu` | **有** |

**真正的墙不是设计系统，是 `super::HubApp`。** 设计系统整体抽成 `devtools-ui` 之后，功能 UI 就能跟着自己的功能一起搬走。

目标 crate 结构：

| crate | 内容 | 行数 | 状态 |
|---|---|---|---|
| `devtools-core` | `Feature` trait · `FeatureCtx` · 注册表 · 配置分片 | ~500 | 新 |
| `devtools-ui` | 设计系统（零互引） | 3.1k | 新 |
| `devtools-platform` | `Pasteboard` / `Screen` / `Ocr` / `Keyboard` / `Floating` trait | ~1.5k | 新 |
| `devtools-clipboard` | 数据模型 + 存储 + 规则 | 2.9k | 已有 |
| `devtools-json` | JSON 处理 | 1.6k | 已有 |
| `devtools-snip` | 截屏 + 标注 + 滚动截图 + 遮罩 UI | ~2.8k | 抽 |
| `devtools-ocr` | OCR 核心 + 结果页 UI | 1.4k | 抽 |
| `devtools-pin` | 贴图 + 贴图 UI | 1.0k | 抽（见 5.2） |
| `devtools-clip-panel` | 剪贴板面板 + 列表 + 预览 | ~1.4k | 抽 |
| `devtools-hub` | main + 窗口容器 + 装配 + 托盘 + 更新 | 剩 ~2k | 收缩 |

`devtools-hub` 剩下的都是宿主职责：窗口容器、注册表路由、`Toast`、托盘、热键服务、设置持久化、更新检查。这些本就不属于任何功能。

### 5.1 有一类功能塞不进统一 trait：多窗口

现在的功能分两种绘制方式：

| 类型 | 功能 | 绘制方式 |
|---|---|---|
| **Page** | 剪贴板面板、JSON 编辑器、OCR 结果页、快捷面板 | 主窗口里的一个页面，hub 管尺寸/位置/焦点 |
| **Viewport** | 截屏遮罩、贴图 | 自建 egui 子视口，自己 `show`/`hide` |

贴图更特殊：**多实例**（`HubApp.pins: Vec<Pin>`，可同时贴多张），每个实例有独立窗口、独立右键菜单、独立状态。

所以 trait 必须显式区分 surface，否则贴图塞不进去：

```rust
pub enum Surface {
    /// 在主窗口内绘制。hub 负责窗口尺寸、位置、焦点、收起。
    Page { window: WindowSpec },
    /// 自建视口，功能自己负责 show / hide。
    Viewport,
}
```

`Surface::Viewport` 的功能用不了 `fn ui(&mut self, ctx, ui)` 那一套，需要另一组钩子：

```rust
pub trait ViewportFeature {
    /// 创建实例（贴图可以创建多个）。
    fn spawn(&self, ctx: &egui::Context, input: ViewportInput) -> Box<dyn ViewportInstance>;
}

pub trait ViewportInstance {
    fn ui(&mut self, ctx: &egui::Context);
    fn is_open(&self) -> bool;
    fn close(&mut self);
}
```

### 5.2 建议：贴图暂时不做插件

它是唯一的「多实例 + 独立窗口 + 右键菜单 + 拖拽缩放」组合，抽象成本远高于其余 5 个。把它留在 hub 由 `Vec<Pin>` 直接持有，其余 5 个走 `Feature` trait——**不要为了统一而把 trait 变成万能接口**。

判断标准：如果一个 trait 里有一半方法是 `Option` 或 `todo!()`，这个抽象就没抽对。

## 6. trait 草案

放在新 crate `devtools-core`（只依赖 `egui` / `epaint` / `serde`，不依赖具体平台）：

```rust
/// 功能的稳定标识：用作页面路由、设置键、热键 id。
pub type FeatureId = &'static str;

/// 一个功能声明自己需要什么、能做什么。
pub trait Feature: 'static {
    fn id(&self) -> FeatureId;
    fn label(&self) -> &'static str;
    fn description(&self) -> &'static str;

    /// 能否处理鼠标中键选中的内容（快捷面板据此筛选）。
    /// 只需 &self，所以快捷面板遍历时不会有借用冲突。
    fn matches(&self, _selection: &Selection) -> bool {
        false
    }

    /// 声明的全局快捷键。默认值与设置键名都由功能自己给出。
    fn hotkeys(&self) -> &'static [HotkeySpec] {
        &[]
    }

    /// 绘制方式与窗口策略：hub 据此决定用自己的窗口还是让功能自建视口。
    /// 功能自己不碰窗口尺寸/位置/焦点。
    fn surface(&self) -> Surface;

    /// 设置页中属于本功能的一段。
    /// 只读自身状态、只改传入的配置分片 —— 这样设置页遍历时不需要 &mut feature。
    fn settings_ui(&self, ui: &mut Ui, cfg: &mut FeatureConfig) {}

    /// 绘制当前页面。需要 &mut self，由 hub 用 Option::take 保证独占。
    fn ui(&mut self, ctx: &mut FeatureCtx<'_>, ui: &mut Ui);
}

pub struct HotkeySpec {
    /// 设置文件里的键名，如 "snip_hotkey"。
    pub key: &'static str,
    pub label: &'static str,
    pub default: &'static str,
}

pub struct WindowSpec {
    pub placement: Placement,
    pub default_size: [f32; 2],
    /// 每个功能记自己的窗口大小（现在散在 Settings 里，靠 size_key 收敛）。
    pub size_key: Option<&'static str>,
    /// 失去焦点是否自动收起。
    pub hide_on_blur: bool,
}

/// 功能绘制时能用到的宿主能力 —— 这是功能与核心之间唯一的缝。
pub struct FeatureCtx<'a> {
    pub shared: &'a Shared,
    pub store: &'a Store,
    /// 按 id 打开另一个功能的页面（跨功能跳转的唯一入口）。
    pub open: &'a mut dyn FnMut(FeatureId),
    pub toast: &'a mut dyn FnMut(String),
}

/// 静态注册表。新增功能 = 加一行，不需要改别的功能。
pub fn registry() -> &'static [Box<dyn Feature>] {
    static CELL: OnceLock<Vec<Box<dyn Feature>>> = OnceLock::new();
    CELL.get_or_init(|| {
        vec![
            Box::new(ClipboardFeature::default()),
            Box::new(SnipFeature::default()),
            Box::new(PinFeature::default()),
            Box::new(OcrFeature::default()),
            Box::new(JsonFeature::default()),
            Box::new(QuickPanelFeature::default()),
        ]
    })
}
```

关键点：

- `FeatureCtx` 是**必须**引入的中间层。少了它，`ui` 里拿不到 `Shared` / `Store`，会退化成直接 `crate::shared::...`，解耦白做。
- 功能**不碰窗口**，只声明 `WindowSpec`。窗口的显示/隐藏/尺寸/焦点是 hub 的职责，所有功能共享这一套逻辑（现在 `hide_panel` / `handle_focus` / `on_shown` 就是这套）。
- `settings_ui` 故意只接收 `&mut FeatureConfig`，不接收 `&mut self`。这让设置页可以遍历所有功能而不产生借用冲突。

## 7. 三个真实难点与解法

### 7.1 egui 的借用冲突（唯一硬技术点）

直接遍历会编译失败：

```rust
for f in &mut self.features {
    f.ui(&mut self.shared, ui); // E0499: cannot borrow `self.shared` as mutable more than once
}
```

**解法**：同一时刻只有一个功能是 active（现在就是 `Page` 单值），根本不需要遍历：

```rust
if let Some(id) = self.active {
    // Option::take 把状态临时掏出来，绘制完放回 —— 独占，无冲突
    let mut feature = self.features.remove(id).expect("active feature");
    feature.ui(&mut FeatureCtx { .. }, ui);
    self.features.insert(id, feature);
}
```

需要 `&self` 的场景（`matches` / `label` / 托盘菜单 / 快捷面板列表）不受影响。
设置页遍历走 `&self` + `&mut FeatureConfig`，也不受影响。

这个坑有干净解法，**不构成否定理由**。

### 7.2 窗口状态机不能倒退

现在这几处按 `Page` 分支硬编码：

| 位置 | 硬编码内容 |
|---|---|
| `HubApp::hide_panel` | 哪个页面保存到哪个 size 字段 |
| `HubApp::handle_focus` | 哪个页面失焦自动收起 |
| `HubApp::on_shown` | 哪个页面要 `refresh` 数据 |
| `HubApp::toast_ui` | 提示条底部偏移（JSON -96 / OCR -64 / 其他 -48） |
| `HubApp::draw` | 哪个页面的 `inner_margin` |

这些都要改成由 `WindowSpec` + trait 钩子驱动，约 100 行改造。改不准确会让「失焦自动收起」「提示条不挡工具栏」这类跨功能行为倒退——这是最容易出回归的地方。

### 7.3 热键的定长假设

`hotkey.rs` 现状：

```rust
pub enum HotkeyAction { Panel, Snip, Pin }
pub const ALL: [HotkeyAction; 3] = [...];
fn index(self) -> usize { self as usize }
```

`HotkeyService::current` 已经是 `HashMap<HotkeyAction, HotKey>`（这部分不用改），但 `ALL` 定长、`index()` 用于 `hotkey_errors: [Option<String>; 3]` 定长数组、事件回调里 `match action { Panel | Snip | Pin }` 三支硬编码。

改成：

```rust
pub type HotkeyId = &'static str;
// 回调统一 post AppEvent::FeatureHotkey(id)，由注册表分派
```

约 60 行改动，`hotkey_errors` 改成 `HashMap<HotkeyId, String>`。

## 8. 迁移顺序

**不要一次定死 trait。** 6 个功能形态差异太大（剪贴板是主面板、截屏是全屏遮罩、贴图是多窗口、OCR 是结果页、JSON 是编辑器），第一版接口大概率不够用。

### 第一步：前置改造（不管做不做 trait 都该做）

1. **`devtools-ocr`**：`snip/ocr.rs` + 两平台的 `ocr.rs` 搬过去，`Line` 改依赖 `epaint`（纯几何+文本，不带 UI 运行时）。
   选它打头，是因为它最小、纯函数、双平台同签名，两小时能跑通 `cargo test`，正好验证「功能间计算依赖」这条模型成不成立。
2. **`devtools-ui`**：设计系统 10 个文件整体搬过去（零互引，纯搬运）。这一步做完，功能 UI 才有资格跟着功能走。
3. **`devtools-platform`**：`Pasteboard` / `Screen` / `Ocr` / `Keyboard` / `Floating` trait + macOS / Windows 两套实现。工作量大但机械。
4. **`Settings` 分片**：`ClipboardSettings` / `JsonSettings` / `SnipSettings` / `OcrSettings`，顶层留 `extras: Map<String, Value>`。

做完这四步的独立价值：`devtools-json` / `devtools-clipboard` 才能真正拿到平台能力（现在只能让 `ui/` 转手），功能间「计算能力依赖」才能用普通 crate 依赖表达，功能 UI 才有地方可去。

### 第二步：trait + 注册表

5. `devtools-core`：`Feature` trait + `FeatureCtx` + `Surface` + `registry()`。
6. `HotkeyAction` → `&'static str`，`Page` enum → `FeatureId`。
7. **只迁移一个功能**（建议 JSON 编辑器：无热键、无特殊 window、无跨功能调用、界面最规整），连 `ui/json_editor.rs` 一起搬进新的 `devtools-json-ui`，验证 trait 够不够用。

### 第三步：渐进迁移

8. 其余功能按「耦合从低到高」迁移，每个搬出去时连 UI 一起搬：
   `JSON` → `剪贴板面板` → `快捷面板` → `OCR` → `截屏` → `贴图`（最后一个，见 5.2）

每个迁移都会暴露 trait 缺什么，补进去再迁移下一个。**不要在第一版就把接口定死。**

**如果只做到第一步就停**，收益仍然成立：平台可复用于未来的 CLI / 测试 / 其他前端，设计系统可复用于任何新窗口，配置不再被核心结构绑死。这部分比插件化本身更划算。

## 9. 回本测算

新增一个功能现在要动的核心文件（以 Base64 编解码为例）：

| 文件 | 改动 | 行数 |
|---|---|---|
| `tools/mod.rs` | `QuickAction` 变体 + `label` / `description` / `matches` + `CONTENT_ACTIONS` | ~10 |
| `ui/mod.rs` | `Page` 变体 + `HubApp` 字段 + `on_shown` / `hide_panel` / `handle_focus` / `draw` 四处 match | ~15 |
| `settings.rs` | 1~2 个字段 | ~2 |
| `ui/settings_page/` | 一个 section | ~5 |

合计约 30 行，**全部落在核心文件里**。

插件化（UI 一起进插件）之后，新增功能变成：

| 动作 | 成本 |
|---|---|
| 新建 crate：`Cargo.toml` + `lib.rs` + `feature.rs` + `ui.rs` | 骨架 ~40 行，一次性模板 |
| `registry()` 加一行 `Box::new(XxxFeature::default())` | 1 行 |
| 核心文件改动 | **0** |

用行数算，40 行 vs 30 行，插件化反而看起来更贵——**因为行数不是重点**。真正变化的是**改动位置**：

| | 现状 | 插件化 |
|---|---|---|
| 改动落在 | 4 个核心文件 | 1 个新 crate + 1 行注册 |
| 冲突面 | 任何人加功能都改同样 4 个文件 | 每人碰自己的 crate |
| 审查范围 | 要看核心 diff | 只看新 crate |
| 核心文件增长 | 线性增长 | 恒定 |

所以「每功能省 20 行」这个算法是错的方向。正确的算法是：**核心文件的改动次数**。现状每个新功能 4 处，插件化 1 处（注册一行）。但要新增 15~20 个功能才能把改造代价摊平——这个量级判断不变。

另一个非量化收益：trait 会强制每个功能把「配置、热键、匹配规则、窗口策略」声明成**数据**，而不是散落在 4 处 match 里。`HubApp` 现在有 5 个页面字段 + 5 处 match；到 10 个功能就是 10 个字段 + 5 处 10 分支 match，那时候是真痛。这个收益在小规模下看不见，但它是防止核心膨胀的唯一手段。

## 10. 明确不做

| 不做 | 理由 |
|---|---|
| dylib 动态加载 / 热加载 | Rust 无稳定 ABI；`Ui` / `Context` 过不了 FFI；插件画不了 egui 界面，液态玻璃、连续曲率圆角、玻璃栏全部失效 |
| 通用事件总线替代 `AppEvent` | 13 个变体的 enum 有穷尽性检查，换成 `Box<dyn Any>` 是纯损失；跨功能跳转只有 5 处，用 `FeatureCtx::open` 足够 |
| 把剪贴板做成插件 | 它是底座：贴图贴剪贴板、OCR 识别剪贴板、JSON 读剪贴板、快捷面板列剪贴板历史 |
| 插件生命周期钩子（`on_load` / `on_unload`） | 编译期注册的功能没有"装载"概念，资源随 `HubApp` 一起创建销毁 |
| 插件配置 schema / 权限声明 | 本项目没有第三方插件，配置就是 `FeatureConfig` 里的 JSON，不需要 schema 校验层 |

## 11. 重新评估的触发条件

出现以下任一情况时，trait 化的收益就从「提前还贷」变成「明显划算」：

- 功能数 ≥ 8~10 个（`HubApp` 的字段和 match 分支开始失控）
- 出现第二个前端（CLI、TUI、iOS），需要复用功能而非 UI
- 出现「用户可装第三方扩展」的产品需求（此时才需要考虑 dylib + 稳定的 C ABI）
