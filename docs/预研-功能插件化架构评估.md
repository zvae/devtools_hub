# 功能模块化架构评估

> 评估“核心宿主 + 编译期注册的功能模块”是否值得做，以及在不破坏现有窗口、快捷键和跨功能流程的前提下，怎样渐进落地。

## 1. 结论

推荐把目标定义为**编译期模块化**，而不是运行时插件系统：每个功能有自己的 crate、状态和 UI，最终由 `devtools-hub` 在编译期装配。它能降低多人新增功能时对 `HubApp`、`Settings` 和路由 `match` 的共同修改；它**不**支持用户安装第三方扩展，也不需要动态库。

当前只有 5 个主窗口页面，且功能目录已经有一定隔离，因此不建议一次性迁移。先完成一个“架构验证试点”，通过后再决定是否全面推进。

| 方案 | 当前建议 | 适用条件 |
|---|---|---|
| 保持 `Page` + `HubApp` | 可继续使用 | 功能总数维持在 6 个左右，新增频率低 |
| 编译期功能模块 + 宿主装配 | **推荐的演进方向** | 功能稳定增长、多人并行开发，或要复用领域能力 |
| dylib / 用户安装第三方插件 | 不做 | 这是另一种产品形态，需要稳定的 C ABI、隔离和版本治理 |

### 开工门槛

在开始迁移现有页面前，必须先验证以下四项：

1. crate 依赖图无环：核心 API 不依赖 hub 或任何 feature；feature 也不反向依赖 hub。
2. 每个 `HubApp` 持有自己的 feature 实例；不存在共享的全局 UI 状态。
3. 跨功能动作能够携带强类型输入，例如图片、选中文本和贴图编辑坐标。
4. 设置文件升级后，未知功能的配置不会被静默丢弃。

任意一项未满足时，先停在目录级拆分，不引入 `Feature` trait。

## 2. 已确认的现状与边界

| 能力 | 已确认现状 | 结论 |
|---|---|---|
| `devtools-clipboard` | 已是独立 crate | 可作为底座继续复用 |
| `devtools-json` | 已是独立 crate，当前仅含 JSON 领域处理 | 可复用，但 JSON 页面尚未独立 |
| OCR 领域逻辑 | `snip/ocr.rs` 负责分块、排序、文本合并；两平台 OCR 入口签名一致 | 最适合做首个领域层拆分 |
| 主窗口路由 | `Page`、页面状态、窗口尺寸、失焦策略和 toast 偏移集中在 `HubApp` | 是新增页面的主要共同修改面 |
| 截屏与贴图 | 通过 egui 子视口运行；贴图支持多实例和原生菜单 | 不能强塞进单页面 trait |
| Settings | 单个 serde struct；未知字段默认会被忽略 | 需要显式的配置兼容策略 |

现有跨功能调用不只有“打开另一个页面”：贴图打开 OCR 要传图片；编辑贴图要传图片、贴图 id 和屏幕位置；快捷面板打开 JSON 要传 `Selection`。因此“按 id 打开功能”只能解决无参数导航，不能作为唯一的跨功能接口。

## 3. 范围与非目标

### 要解决

- 新功能的状态、UI、设置和热键声明尽量留在自己的 crate。
- 宿主统一管理主窗口的显示、尺寸、焦点、托盘、热键注册和持久化。
- OCR、剪贴板、JSON 等领域能力可被后续 CLI 或其他前端复用。
- 保持已有的截图、贴图、OCR、粘贴和失焦行为。

### 明确不做

- 不加载 dylib / dll，不做热加载或第三方插件市场。
- 不用 `Box<dyn Any>` 替换现有 `AppEvent`；有限枚举与强类型端口保留穷尽性检查。
- 不把剪贴板存储层当作可卸载插件；它是多个功能的基础服务。
- 第一阶段不迁贴图。它是多实例视口功能，应先保留在 hub。
- 不预先设计 `on_load` / `on_unload` 等动态插件生命周期。

## 4. 目标依赖图

核心原则只有一条：**依赖朝 API 和领域层单向流动，装配只发生在 hub。**

```text
devtools-feature-api        devtools-ui-foundation       devtools-ocr-domain
          ▲                         ▲                         ▲
          │                         │                         │
  feature-json / feature-ocr / feature-panel / feature-snip
          ▲                         ▲                         ▲
          └────────────── devtools-hub（装配、平台适配、窗口宿主）
                                     ▲
                         devtools-platform-api / 平台实现
```

建议的职责如下：

| crate / 层 | 允许依赖 | 不能依赖 | 职责 |
|---|---|---|---|
| `devtools-feature-api` | `egui`、serde、基础领域类型 | hub、任意具体 feature | `FeatureId`、页面元数据、宿主端口接口 |
| `devtools-ui-foundation` | egui、纯样式资源 | 原生窗口控制、hub | 字体、图标、色板、通用控件、代码样式 |
| `devtools-ocr-domain` | image、epaint、anyhow | 平台实现、UI | `Line`、分块识别、阅读顺序、文本合并 |
| `devtools-platform-api` | 必要的领域类型 | hub UI | `Screen`、`Pasteboard`、`Keyboard` 等端口 |
| feature crate | API、领域 crate、UI foundation | hub 私有模块 | 功能状态、UI、功能私有设置、元数据 |
| `devtools-hub` | 上述全部 | — | 组装、平台实现、主窗口状态机、托盘、更新 |

现有 `ui/` 的 10 个文件不能整体按“零互引”搬走：`style` 依赖字体和图标，`native_menu`、`widgets`、`textures` 又直接使用平台能力。应先分为 `ui-foundation` 与仍留在宿主的 native UI adapter；不要把这一步估算成纯搬运。

同理，平台层现在还使用 `snip` 的 `Display`、`ScreenWindow` 和图像工具。因此应先抽出 OCR / 截图的共享领域模型，或将平台 API 按能力拆开；不能先搬整个 `platform` crate 再补依赖。

## 5. 注册与状态模型

`Feature` trait 可以存在，但核心 API crate 不应直接构造 `JsonFeature`、`OcrFeature` 等实现。否则它既需要依赖所有 feature，又会和 feature 对 API 的依赖形成环。

注册表也不能保存全局的 `Box<dyn Feature>`：功能 UI 有可变状态，而同一进程可能创建测试 app 或重新初始化 app。正确模型是“静态描述符 + 每个 app 自己创建实例”。

```rust
// devtools-feature-api
pub type FeatureId = &'static str;

pub struct FeatureDescriptor {
    pub id: FeatureId,
    pub label: &'static str,
    pub description: &'static str,
    pub create: fn() -> Box<dyn Feature>,
}

pub trait Feature {
    fn render(&mut self, ctx: &mut FeatureCtx<'_>, ui: &mut egui::Ui);
}

// devtools-hub：唯一的 composition root
fn descriptors() -> &'static [FeatureDescriptor] { /* feature 的 factory 列表 */ }
fn build_features() -> FeatureMap { /* 对每个 descriptor 调用 create */ }
```

`FeatureDescriptor` 只放声明性数据；`HubApp` 以 `FeatureId` 路由，并独占取出 active feature 后再绘制。这样可避开 egui 的可变借用冲突，且不会产生全局共享状态。

## 6. 宿主接口与跨功能调用

`FeatureCtx` 是必要的边界，但它不能直接公开 `HubApp`、`Shared` 或任意具体 feature 的内部状态，否则只是把 `crate::` 路径换了名字。它应该只暴露少量稳定的宿主能力，例如 toast、持久化、当前窗口操作和受限的数据端口。

```rust
pub struct FeatureCtx<'a> {
    pub host: &'a mut dyn HostServices,
    pub navigation: &'a mut dyn Navigation,
}

pub trait Navigation {
    // 仅用于无参数的页面切换。
    fn open(&mut self, target: FeatureId);
}
```

带输入的跨功能调用使用**窄、强类型端口**，不要藏进无类型消息：

| 调用 | 推荐端口 | 输入 |
|---|---|---|
| 截屏 / 贴图 → OCR | `OcrLauncher::open` | `Arc<RgbaImage>` |
| 贴图 → 截屏编辑 | `SnipEditor::edit_pin` | 图片、贴图 id、屏幕矩形 |
| 快捷面板 → JSON | `JsonLauncher::open` | `Option<Selection>` |
| 快捷面板 → 剪贴板 | `Navigation::open` | 无 |

这些端口由目标 feature 的 API crate 定义、由 hub 的 feature registry 适配并注入来源 feature。它们是明确依赖，不是通用事件总线。后台线程仍可继续向 hub 发送有限的 `AppEvent`；只把需要跨线程唤醒的事件放进去。

## 7. 页面与视口的边界

主窗口页面与独立视口不是同一类抽象：

| Surface | 功能 | 所有者 |
|---|---|---|
| 主窗口 Page | 剪贴板面板、设置、快捷面板、JSON、OCR | hub 管窗口位置、尺寸、焦点与收起 |
| 独立 Viewport | 截屏遮罩、贴图 | feature 管自己的视口绘制；hub 保持 eframe 生命周期 |

第一版 `Feature` 只覆盖 Page。窗口元数据应至少表达默认尺寸、尺寸配置键、边距、失焦收起策略及 toast 安全区域；不要只用 `WindowSpec` 的一个 `hide_on_blur` 布尔值替代现有状态机。

贴图暂留 hub。迁移清单中也不应把它标成“最后迁移”，除非后续单独完成多实例视口生命周期的设计和试点。

## 8. 配置与热键

顶层设置仍保留真正的全局项，例如面板位置、主题、托盘、更新策略和共享剪贴板策略。功能设置使用有命名空间的容器：

```rust
pub struct Settings {
    pub global: GlobalSettings,
    pub features: BTreeMap<String, serde_json::Value>,
}
```

每个 feature 在自己的 crate 中把 `Value` 反序列化为强类型配置，并在失败时采用默认值、保留原始值并记录可诊断日志。迁移时须明确旧字段到新命名空间的映射。

不能仅加一个普通 `extras: Map` 字段；serde 对未知字段默认会忽略，旧版本或暂未加载功能的配置会被保存动作静默删除。最低限度的回归测试包括：旧 `settings.json` 升级、未知 feature 配置往返保存、损坏的单个 feature 配置降级、热键冲突与禁用热键。

热键仍由 hub 注册。feature 只声明 `HotkeySpec { id, label, default }`；hub 用 `HashMap<HotkeyId, HotKey>` 和 `HashMap<HotkeyId, String>` 记录当前注册与错误。面板开关这样的宿主快捷键不要伪装成普通 feature 热键。

## 9. 分阶段计划与验收

### 阶段 0：架构验证试点（先做，1–2 个工作日，置信度中）

1. 新建空的 `devtools-feature-api`，只放 ID、descriptor 和宿主端口接口。
2. 在 hub 用一个假的 JSON feature factory 创建 per-app 实例。
3. 验证 `cargo tree -p devtools-hub` 中没有 feature → hub 的反向依赖，也没有循环。
4. 用现有离屏 UI 测试证明重复创建 `HubApp` 不共享 feature 状态。

通过标准：依赖图成立、主窗口仍可显示/隐藏、测试 app 之间没有状态泄漏。失败则撤回 trait 方案，继续采用目录级模块化。

### 阶段 1：可独立获益的领域拆分（1–2 周，置信度中）

1. 抽 `devtools-ocr-domain`：`Line`、平铺、排序和文本合并；保留并迁移现有单元测试。
2. 将 macOS / Windows OCR 实现改为该领域层的 adapter，验证两平台类型检查。
3. 划分 `ui-foundation` 与 native adapter；只迁移没有平台依赖的样式、字体、图标和控件。
4. 设计并测试 Settings 配置容器与旧 JSON 的升级路径。

这阶段即使停止，也能为 CLI、测试或其他前端复用 OCR 与基础 UI，不依赖完整插件化的收益成立。

### 阶段 2：JSON 页面试点（3–5 个工作日，置信度低到中）

迁 JSON 的状态与 UI，接上配置、快捷面板输入和主窗口窗口策略。JSON 不是“零耦合”页面：它当前直接扩展 `HubApp`，并使用快捷面板的图标绘制与 `Selection`。试点应以完整行为而非能否编译为验收。

验收：快捷面板打开 JSON、JSON 文件大小限制、固定/失焦隐藏、窗口尺寸持久化、toast 安全位置、原有快照测试全部通过。

### 阶段 3：是否全面迁移

只在 JSON 试点没有新增临时逃生口（例如 `FeatureCtx` 暴露 `HubApp`）时，才按“剪贴板面板 → 快捷面板 → OCR → 截屏”的顺序迁移。贴图继续保持宿主所有。

完整迁移的工作量在试点前不做精确承诺；Windows 原生窗口、视口和焦点行为的回归验证会决定关键路径。预期是数周而非“纯骨架数百行”的工作量。

## 10. 回本与重新评估条件

模块化的回报不是“每个功能少写几行”，而是减少 `HubApp`、`Settings`、热键和路由分支的共同修改与合并冲突。当前规模下，这个收益还不压倒迁移成本。

出现以下任一信号时，应重新评估全面迁移：

- 主窗口功能稳定达到约 8–10 个，`HubApp` 的字段与 `match` 分支持续增长。
- 同时有两名以上开发者频繁增加或修改不同功能。
- 需要 CLI、TUI 或第二个图形前端复用 OCR、剪贴板、JSON 等领域能力。

若未来出现用户可安装第三方扩展的产品需求，应另立设计：稳定 C ABI、进程隔离或 RPC、权限模型、版本兼容、崩溃隔离和 UI 协议都属于新项目范围，不能在本方案上直接追加 dylib 加载。
