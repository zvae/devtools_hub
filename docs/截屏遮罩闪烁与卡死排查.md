# 截屏遮罩：闪烁、错位与卡死的排查记录

截屏遮罩（`ui/snipper`）是一个盖住整个显示器的窗口，上面画着截屏时拍下的静止截图。遮罩出现、收起的那一刻，只要它和真实屏幕有一点不一致，用户看到的就是“整个屏幕闪了一下”；它一旦不再响应输入，整个屏幕就点不了。这份记录按时间顺序整理了几个相关问题的现象、证据、原因和修改，最后是排查方法和经验。

## 现象

| # | 平台 | 现象 | 结论 |
| --- | --- | --- | --- |
| 1 | macOS | 截屏结束（贴图、保存、复制、关闭）时整屏模糊一下 | 遮罩视口被销毁又重建，新窗口带着默认动画收起（见原因 1） |
| 2 | macOS | 修了一轮后仍偶发：整个画面被纵向压扁、错开一帧，菜单栏和程序坞出现两份 | 同上，是同一个问题的另一种表现 |
| 3 | macOS | 截屏时点保存，紧接着再截屏，整个屏幕锁死，按什么都没反应，只能强制关机 | 下一次截屏沿用了上一次残留的遮罩窗口（推断，见原因 3） |
| 4 | macOS | 终端里出现 `-[NSAutoreleasePool drain]: This pool has already been drained, do not release it (double release).` | 关闭贴图时系统移除 KVO 观察者抛了异常（见原因 4） |
| 5 | Windows | 截屏开始时先出现一块白色、再是左上角一块画面加大片黑色；结束时整个画面错开约 1 像素 | 遮罩一创建就可见、按错误的尺寸创建；客户区与窗口矩形不重合（见原因 5） |

## 排查方法

这些问题都只持续一两帧，肉眼看不清，日志里也没有错误，主要靠录屏逐帧分析和临时诊断日志：

- **逐帧抽取录屏**：本机没有 ffmpeg，用 AVFoundation 写了个 Swift 小脚本（`AVAssetImageGenerator`，前后容差设为 0），按 1/30 秒取帧存成 PNG。
- **找出变化的帧**：用 Python + Pillow 计算每帧的平均亮度和与上一帧的差（`ImageChops.difference`），差值突然变大的帧就是遮罩出现、收起或闪烁的时刻。
- **区分“模糊”和“编码失真”**：用边缘检测（`ImageFilter.FIND_EDGES`）的方差衡量清晰度。现象 1 里清晰度在 3 帧内先降后升（4178 → 2359 → 1548 → 3707），是一段真实的动画，不是视频编码造成的偶发模糊。
- **测量错位的几何**：把正常帧切成一条条横带，在闪烁帧里找每条横带最匹配的位置，拟合出纵向映射 `y' = 0.879·y + 52`（录屏坐标）。换算到屏幕坐标，就是截图被画进了一个约 1920×949、上边缘在 y≈62 的区域。
- **临时记录窗口状态**：在主界面和遮罩的每一帧里列出本应用所有 `NSWindow` 的标题、类、frame、alpha、层级、是否可见、动画行为，状态有变化就记一条日志。排查完已删除。现象 2 的原因就是靠它找到的。
- **系统日志**：`/usr/bin/log show --start … --end … --style compact`，按进程号、线程号过滤。注意 zsh 里的 `log` 是内建命令，要写全路径。现象 3、4 的时间线和异常都来自系统日志。
- **最小复现实验**：KVO 的问题用 Swift 写了个几十行的程序，复现“按类 A 登记观察者 → 换成类 B → 移除时抛异常”。

## 原因 1：截屏结束那一帧，遮罩视口被销毁又重建（现象 1、2）

### 证据

临时记录的窗口状态（节选，截屏 15）：

```
截屏开始：#30982 "DevTools Hub 截屏 15" WinitWindow frame=(0,0,1920×1080) level=1000
贴图 #15 创建后：#30982 消失
#30986 "DevTools Hub 截屏 15" WinitWindow frame=(0,67,1920×951) level=3 alpha=1.00
```

截屏一结束，原来的遮罩窗口 #30982 就没了，紧接着出现一个同名的新窗口 #30986。它的 frame 被系统限制在菜单栏和程序坞之间（AppKit 坐标，左下角为原点：从 y=67 起高 951，即屏幕坐标的 62 到 1013），正好是录屏里测出来的压扁区域。

### 原因

- egui 的规则：**哪一帧没有调用 `show_viewport_deferred`，这个视口的窗口就在这一帧结束时被销毁**。
- `Snipper::show` 拿到截屏结果的那一帧提前 `return`，没有调用它，遮罩窗口被销毁。
- 下一帧，收起遮罩的过渡（`closing_snip_ui`，先把焦点还给原来的应用、遮罩再停留一会儿）又调用了 `show`，egui 就新建了一个窗口。
- 新窗口没有经过 `floating::begin_overlay`：位置被系统限制，层级是普通的置顶，动画行为是默认值。它一旦画出静止截图，就是那一帧压扁错位的画面；收起时默认的缩放淡出动画就是现象 1 的整屏模糊。
- 新窗口大多数时候是透明的（没有重绘就什么都不显示），所以现象 2 是偶发的。

### 修改

- `Snipper::show` 在返回结果的那一帧也调用 `show_viewport_deferred`，遮罩从截屏结束到收起始终是同一个窗口（`ui/snipper/mod.rs`）。结果是保存时例外，见原因 3。
- `begin_overlay` 里 `setAnimationBehavior(NSWindowAnimationBehavior::None)`，关掉遮罩显示、收起时的动画（`platform/macos/floating.rs`）。

### 走过的弯路

现象 1、2 前后修了好几轮，前几轮都没找到根因：

1. 以为是遮罩自己 `orderOut` 时的动画，关掉了遮罩的动画。保留了下来（本来就该关），但真正在播动画的是重建出来的那个窗口。
2. 以为是收起时窗口被系统变换，改成先把 alpha 设为 0、50 ms 后再收起。完全没用，因为设成透明的是原来的窗口，闪的是新窗口。已删除。
3. 以为是上一次截屏的遮罩窗口还没释放、按标题找错了窗口，给每次截屏的遮罩起了不同的标题，并在日志里记录残留的窗口数。日志显示没有残留窗口，第一次截屏也会闪，这个猜想被否定，改动回退了。（后来因为原因 3，每次截屏又改成了不同的视口和标题。）

直到把所有窗口的状态都记进日志，才看到窗口被重建。**猜测、修改、再测试的循环很慢，先把状态记下来要快得多。**

## 原因 2：遮罩收起时原来的应用还没恢复（预防性修改）

截屏期间本应用在前台（遮罩要接收按键、改变鼠标指针），原来的应用处于非活跃状态（侧栏、标题栏变灰），只是被静止的截图挡住了。如果先收起遮罩再还焦点，中间会露出一帧整屏的非活跃外观。

最初的做法是先还焦点、遮罩固定停 200 ms 再收起。但应用重新激活是异步的，Electron 应用可能要几百毫秒，所以改成：

- 每帧检查原来的应用是否已经回到前台（`NSRunningApplication.isActive`，见 `floating::focus_restored`）。
- 回到前台后遮罩再停 60 ms，等它把窗口重画成活跃的样子；最少停 200 ms，最多 1 秒（`ui/screenshot.rs` 的 `CLOSE_*` 常量）。

实测原来的应用约 130～160 ms 回到前台，遮罩约 260 ms 后收起。注意：原因 1 修好之前，原来的遮罩窗口在结束那一帧就被销毁了，这个“停留一会儿”其实一直没有生效。

## 原因 3：保存后紧接着截屏，遮罩卡住、锁住整个屏幕（现象 3）

### 时间线（系统日志）

| 时间 | 事件 |
| --- | --- |
| 09:45:55 | 截屏 A，遮罩出现，本应用成为前台 |
| 09:45:57 | 在截屏 A 里点保存，系统的保存对话框服务（`openAndSavePanelService`）启动，主线程进入模态循环 |
| 09:46:00.46 | 对话框关闭，焦点还给终端 |
| 09:46:00.61 | 截屏 B 开始截图（快捷键事件在模态期间被 winit 排队，对话框关闭后才处理） |
| 09:46:00.86 | 截屏 B 的遮罩出现，本应用成为前台 |
| 之后 | 键盘事件都送到了本应用（WindowServer 日志 `keyboardFocus; pid: …`），但遮罩没有任何反应；主线程仍在处理 AppKit 事件（`performKeyEquivalent`） |

### 原因（推断，没有复现）

- 原因 1 的修改让 `show` 在返回结果的那一帧也维持遮罩视口，包括点保存的那一帧。保存时遮罩立即收起，但视口没有被销毁。
- 对话框关闭后，面板是隐藏的，又没有贴图，**eframe 只调用 `logic`，不运行界面**。只有运行界面的那一帧才会清理没人维持的视口，所以截屏 A 的遮罩窗口一直残留着（已经收起，但没有销毁）。
- 所有截屏共用同一个视口 id，截屏 B 就沿用了这个残留的窗口。eframe 记录的窗口状态（是否可见等）与实际不一致，结果遮罩被摆到了最上层，却不再绘制、也不处理输入。遮罩的层级在菜单栏和程序坞之上，整个屏幕就被盖住了。

### 修改

- 每次截屏的遮罩都是新的视口：视口 id 和窗口标题都带上截屏编号（`NEXT_SNIP`），不会沿用上一次的窗口（`ui/snipper/mod.rs`）。
- 结果是保存时，那一帧不维持遮罩视口，窗口在这一帧结束时就被销毁。
- **兜底的看门狗**（`ui/snipper/watchdog.rs`）：遮罩正常时，鼠标在它上面一动就会重绘（放大镜、十字光标跟着鼠标）。后台线程每 200 ms 读一次鼠标位置，鼠标在遮罩所在的显示器上动了、之后 10 秒都没有重绘，就判定遮罩卡住了：
  - macOS：用 libdispatch 的 `dispatch_async_f` 把“收起遮罩、还焦点”投递到主队列执行（`floating::rescue_overlay`），不经过 eframe。主队列在模态对话框等嵌套的 run loop 里也会执行，这次锁屏时主线程正是还在跑 AppKit 事件、只是 eframe 不响应。主线程彻底死锁时这个办法无效。
  - Windows：用 `ShowWindowAsync` 隐藏遮罩，窗口所在的线程卡住时也不会阻塞；焦点要用户自己点别的窗口切换。
  - 主界面在 `logic` 里收到通知后丢掉截屏状态（`check_snip_rescued`），下次截屏照常开始。

## 原因 4：贴图换类后，关闭时 KVO 抛异常（现象 4）

### 证据

警告前 7 ms，同一个线程上：

```
Cannot remove an observer <NSKVOForwarder 0x…> for the key path "_windowLayerContext"
from <DevToolsHubPin 0x…> because it is not registered as an observer.
```

### 原因

- 贴图要做成不激活应用的面板，`floating::configure_pin` 把 winit 创建的窗口实例的类换成了 `NSPanel` 子类 `DevToolsHubPin`（`panel::make_nonactivating`）。
- KVO 本身也靠换类工作：被观察的对象的类会被换成动态生成的 `NSKVONotifying_原类名`，观察者的登记是按原来的类记下的。
- 代码只把 winit 登记的 `effectiveAppearance` 观察者先移除、换类后再加回。系统自己也在观察窗口（视图经由 `NSKVOForwarder` 观察 `_windowLayerContext`），这条登记没法移除再加回。
- 关闭贴图时，系统按新类去找这条登记，找不到就抛 `NSInternalInconsistencyException`。异常展开时提前释放了 autorelease pool，随后系统再 drain 它，就打出了 “already been drained”。ObjC 异常穿过 Rust 栈帧是未定义行为，有崩溃的风险。

### 验证

Swift 实验：对象先按类 A 被观察（经由 key path `inner.ctx` 产生 `NSKVOForwarder`），换成类 B 后移除观察者，抛出同样的 “Cannot remove an observer … for the key path” 异常；销毁前先换回类 A 再移除，正常。

### 修改

- 换类的逻辑抽成 `panel::swap_class`，并新增 `panel::original_class`，在换类前记下原来的类（KVO 改写过 `-class`，返回的就是原来的类）。
- 贴图关闭、窗口销毁前调用 `floating::release_pin`：先收起窗口，再按同样的步骤换回原来的类，系统移除观察者时登记就能对上（`ui/screenshot.rs` 的 `pins_ui`）。
- 主面板也换了类，但它一直存在到应用退出，退出走 `process::exit`，不会销毁窗口，所以不用处理。

## 原因 5：Windows 上的遮罩（现象 5）

录屏是远程桌面里的 Windows，截屏开始时依次是：

1. 一块白色，只有屏幕约 2/3 大：遮罩是不透明窗口（Windows 上 wgpu 的透明窗口不稳定），一创建就可见，第一帧画出来之前显示的是白底；winit 按创建时的缩放换算逻辑尺寸，窗口只有屏幕的一部分大。
2. 左上角一块画面加大片黑色：`begin_overlay` 把窗口铺满屏幕后，第一帧还按旧尺寸画，其余部分是黑的。
3. 正常铺满。

结束时整个画面错开约 1 像素：winit 的无边框窗口保留了部分边框样式，客户区不一定与窗口矩形重合，按窗口矩形摆放时截图就错开了。

修改（`platform/windows/floating.rs`）：

- 用 `DWMWA_TRANSITIONS_FORCEDISABLED` 关掉 DWM 给遮罩、贴图加的淡入淡出（相当于 macOS 上关掉窗口动画）。
- 遮罩隐藏着创建（`OVERLAY_STARTS_HIDDEN`，macOS 上为 false，那里的遮罩是透明窗口，创建时什么都不显示）。
  - eframe 不运行隐藏窗口的界面，所以由主界面把它显示出来（`show_overlay`）：先用 `DWMWA_CLOAK` 遮住，摆好位置后再显示。
  - 遮罩按铺满屏幕的尺寸画好一帧后才去掉遮挡（`reveal_overlay`，判断方法见下文“原因 6”）。
  - 面板隐藏时 eframe 只调用 `logic`，所以为创建遮罩临时唤醒的面板要等遮罩显示出来再收起（`ui/mod.rs` 里的 `finish_wake`）。
- 摆放遮罩时先按窗口矩形摆，再按客户区与目标的偏差修正一次，让客户区正好铺满显示器（`place_overlay`）。

## 原因 6：Windows 上遮罩露出来的第一帧整屏放大（现象 5 的后续）

### 现象与证据

原因 5 修改后在 Windows 本机（3840×2160，缩放 175%，Vulkan 后端）实测：按 F1 后先出现一帧“整屏放大”的画面，然后才是正常的遮罩。逐帧测量：画面横向放大约 1.33 倍、纵向约 1.42 倍，原点在左上角，只显示了截图左上约 75%×70% 的一块。

用 ffmpeg 的 `ddagrab`（桌面复制 API，抓的是 DWM 合成后的画面，被 cloak 的窗口不会出现）以 60fps 录屏、模拟按 F1：修改前 3/3 次都出现，持续约 11 帧（调试版）。

### 原因

- 摆放遮罩的 `SetWindowPos` 在界面回调里同步执行，winit 把随之产生的 `Resized` 排进队列，回调返回后才交给 eframe 去调整交换链尺寸（`Painter::on_window_resized`）。
- egui 每帧直接读窗口当前尺寸（`window.inner_size()`）排版，于是摆好窗口的那一帧按铺满屏幕排版、却画进旧尺寸的交换链：只画出左上一块，DWM 再把它拉伸到整个窗口。
- 原来的判断是“摆好窗口的下一帧就露出来”，露出来时屏幕上显示的正是这一帧。
- 只改成“上一帧的交换链尺寸正确就露出来”也不够：临时日志显示这样判断时第二帧就满足了，但录屏里露出来后仍有几帧拉伸。按新尺寸画的帧已经提交，GPU 还没画完（第一次截屏要上传整屏的截图纹理），屏幕上还是旧的那一帧。

### 修改

- 遮罩里放一个什么都不画的 wgpu 绘制回调（`ui/snipper/reveal.rs`）：在 `prepare` 里从 `ScreenDescriptor` 记下每帧实际画进去的交换链尺寸；上一帧的尺寸等于显示器尺寸时，用 `Queue::on_submitted_work_done` 等这一帧在 GPU 上画完，才去掉遮挡。
- 遮住的窗口收不到鼠标事件、不会自己重绘，露出来之前每帧 `request_repaint`；等 60 帧还没等到（比如不是 wgpu 渲染）就直接露出来，免得遮罩一直遮着。
- 修改后 4/4 次只有一次跳变（桌面直接变成遮罩），包括启动后的第一次截屏。

## 经验

1. **egui 延迟视口的生命周期**：哪一帧没有调用 `show_viewport_deferred`，窗口就在这一帧结束时被销毁；之后再调用会新建窗口。凡是“结束后还要停留一会儿”的窗口，结束的那一帧也要维持。
2. **eframe 只调用 `logic` 的帧不清理视口**：面板隐藏、又没有可见的子窗口时，eframe 不运行界面，没人维持的视口会残留下来。不要指望“不调用就会被销毁”，需要一个全新的窗口时用新的视口 id。
3. **按标题找原生窗口时，标题要唯一**：eframe 不提供子视口的原生句柄，平台层只能按标题找窗口。同一时刻可能存在两个同名窗口时，找到的未必是想要的那个。
4. **换类与 KVO**：给系统或框架创建的对象换类之前，要想到 KVO 的登记是按原来的类记下的。自己能处理的观察者可以先移除再加回，系统的处理不了，对象销毁前要换回原来的类。
5. **盖住整个屏幕的窗口要有兜底**：它一旦不响应，用户连退出都做不到。兜底逻辑不能依赖可能卡住的那套事件循环。
6. **“整屏闪一下”先逐帧看录屏**：亮度差找时刻，清晰度区分动画和编码失真，横带匹配测几何。测出来的几何尺寸（1920×949、y≈62）直接指向了“窗口被系统限制在可见区域内”。
7. **先记状态，再猜原因**：这次在没有证据的猜测上浪费了三轮修改。窗口列表、系统日志这类状态一旦记下来，原因通常一眼就能看出来。
8. **模态循环期间 winit 会把事件排队**：在界面代码里弹出模态对话框（`runModal`）时，期间的快捷键等事件要等对话框关闭后才处理，不会重入。

## 复查方法

- **闪烁**：录屏后逐帧看遮罩出现、收起前后的几帧，画面应该完全一致，不应出现模糊、压扁、错开、放大、白块或黑边。
  - Windows 上可以自动化：`ffmpeg -f lavfi -i "ddagrab=framerate=60:draw_mouse=0,hwdownload,format=bgra" -vf scale=960:-1 -t 3 f_%03d.png` 录屏，期间用 `keybd_event` 模拟按 F1；再把帧缩成 192×108 灰度原始数据（`-f rawvideo`），算相邻帧的平均差。正常情况按 F1 后只有一次跳变，出现两次跳变说明中间有一帧不对。
- **遮罩是否被重建**：临时在主界面和遮罩的每一帧列出本应用的窗口（标题、frame、层级），截屏结束到收起期间遮罩窗口的编号不应变化。
- **锁屏**：截屏时点保存，对话框关闭后立刻再截屏，遮罩应正常响应。看门狗可以临时把 `STALL` 改小、去掉遮罩回调里的 `watchdog::frame_painted()` 来验证强制收起（不要用死循环模拟：主线程整个卡死时，投递到主队列的收起操作也执行不了）。
- **KVO 异常**：开几个贴图再逐个关闭，终端里不应出现 “Cannot remove an observer” 和 “already been drained”。
