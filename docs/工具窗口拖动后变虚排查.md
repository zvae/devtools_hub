# 工具窗口拖动后变虚排查

## 现象与排查

用户反馈所有工具窗口拖动后变虚，点击窗口按钮后恢复。补充的 Base64 对比图中，
拖动后的小字与控件边缘更淡、更软，标题相对清楚。第一次只在原生拖动返回后
请求重绘，用户复测仍然出现，因此不能把缺少重绘认定为根因。

普通工具共用主面板窗口，`ToolEffect::StartDrag` 经宿主交给 macOS 的
`performWindowDragWithEvent:`。这会在界面回调尚未结束时进入原生拖动循环，
eframe 的正常窗口更新和鼠标事件处理需要等待它返回。原有实现还需要重建鼠标事件，
避免窗口激活事件被误当成拖动起点。

自动化界面工具能打开独立的 Base64 调试窗口和操作按钮，但未可靠触发这条原生拖动路径。
尚未取得足以确定是鼠标释放状态、窗口层提交还是像素插值导致变虚的运行时证据。

## 当前处理

绕开这条原生拖动路径，采用仓库贴图窗口已有的逐帧移动方式：

- `panel::start_drag` 只记录鼠标相对窗口的位置，不进入阻塞的原生拖动循环。
- `HubApp::logic` 在拖动期间每约 16 ms 调用 `panel::update_drag`，读取系统鼠标位置移动窗口。
- 读取系统左键状态，松开后完成最后一次位置更新并停止排帧；隐藏窗口也清除拖动状态。
- 根据鼠标所在显示器的缩放比例将窗口位置对齐到物理像素，并保留普通窗口的屏幕边界约束。
- 工具、剪贴板面板、设置和 OCR 的自绘拖动区域共用同一入口；Windows 继续通过 winit 拖动。

不增加空闲轮询，不改变背景透明度、玻璃材质或文字配色。

## 验证范围

回归测试覆盖鼠标抓取点不跳动、负坐标显示器、1× / 2× 像素对齐，以及窗口不存在时结束拖动并停止排帧。
编译检查、全量测试和工具离屏快照用于检查代码与界面回归，无法证明原生拖动的视觉问题已经消失。

实机复测需要分别在同一显示器内和不同缩放比例的显示器之间拖动，松开后不再点击，
确认文字和图标保持清晰、鼠标松手后窗口停止跟随、拖动起点不跳动，窗口内按钮仍正常响应。
