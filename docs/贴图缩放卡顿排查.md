# 贴图滚轮缩放卡顿排查

## 现象

macOS 上用滚轮 / 触控板缩放贴图时一卡一卡的。第一次修改（把 `InnerSize`、`OuterPosition` 两个视口命令合成一次 `setFrame:display:`，见下文“修改”第 2 点）后仍然卡。

## 测量

在 `PinState::ui` 里临时加了一段代码（排查完已删除）：设置环境变量后贴图每帧自己放大或缩小 3%（放大到 160% 后缩小到 60%，来回），并在日志里记下每帧的间隔、`sync_window` 的耗时和窗口大小。用 `--pin` 贴一张 800×500 的截图，运行 6 秒（debug 构建）：

| | 帧数 | 帧间隔中位数 | 最长帧间隔 | `sync_window` |
| --- | --- | --- | --- | --- |
| 修改前 | 31 | 8 ms | 1009 ms | 约 0.2 ms |
| 修改后 | 359 | 16.8 ms（p99 21 ms） | 46 ms | 约 0.3 ms |

修改前的帧间隔序列（节选）：放大时每帧约 8 ms，很流畅；**缩小时每两三帧就有一帧间隔约 1.007 秒**：

```
8.826084ms  1.605 [1284.0 802.0]
19.860875ms 1.558 [1246.0 779.0]
1.008699333s 1.513 [1210.0 756.0]
5.203875ms  1.469 [1175.0 734.0]
6.687958ms  1.426 [1141.0 713.0]
1.006210875s 1.384 [1107.0 692.0]
```

改变窗口大小本身很快（`sync_window` 不到 1 ms），时间花在别处。

## 原因

1. eframe 0.36 在 macOS 上收到窗口的 `Resized` 事件时，认为窗口进入了“实时调整大小”（用户拖动窗口边缘），
   调用 `Painter::on_window_resize_state_change(id, true)`；**直到这个窗口收到一个既不是 `Resized` 也不是 `Moved` 的事件**，
   才认为调整结束（`eframe/src/native/wgpu_integration.rs` 的 `on_window_event`，注释引用 egui#903）。
2. egui-wgpu 的默认特性 `macos-window-resize-jitter-fix` 在进入、退出这个状态时打开、关闭 CAMetalLayer 的
   `presentsWithTransaction` 并重新配置 surface（`egui-wgpu/src/winit.rs` 的 `on_window_resize_state_change`）。
   打开后，画面的呈现要跟随 CoreAnimation 事务提交，用来消除用户拖动窗口边缘时内容的抖动。
3. wgpu 的 Metal 后端把 `allowsNextDrawableTimeout` 设为 false（`wgpu-hal/src/metal/surface.rs`），
   `nextDrawable` 拿不到可用的 drawable 时会一直等，不会超时返回空。
4. 贴图缩放是程序改变窗口大小，没有用户拖动时 AppKit 驱动的那套事务流程。自动缩放期间窗口只收到 `Resized` / `Moved`，
   一直处在“实时调整大小”状态；用真实滚轮缩放时，滚轮事件又会让它每一步都退出、再进入，每一步重新配置两次 surface。

据此推断：卡顿是 `presentsWithTransaction` 打开时，画面绑在没有人及时提交的事务上，drawable 迟迟不释放，下一帧的
`nextDrawable` 被阻塞（每次约 1 秒；为什么正好约 1 秒、为什么缩小时更明显没有查清）。日志里没有 egui-wgpu 的
“Dropped frame” 警告（项目的 tracing 经 tracing-log 收集 `log` 的输出），说明不是取帧失败后跳帧，而是取帧这一步卡住了，
与推断一致。直接证据是下面第 1 点：关掉这个特性后卡顿完全消失。

## 修改

1. **关掉 `macos-window-resize-jitter-fix`**（`Cargo.toml`）：eframe 改为 `default-features = false`，用 `wgpu_no_default_features`
   代替 `wgpu`（`wgpu` 会带上 egui-wgpu 的全部默认特性），其余特性与默认一致；另外直接依赖 `wgpu = "30"`，
   让 wgpu 的默认特性（各平台的图形后端）照常打开。Linux / Web 专用的 `wayland`、`x11`、`web_screen_reader` 一并去掉，
   `Cargo.lock` 少了一批 wayland / x11 相关的依赖。
2. **一次设置窗口的位置和大小**（`floating::set_window_frame`）：macOS 用 `setFrame:display:`，Windows 用一次 `SetWindowPos`。
   分成 egui 的 `InnerSize`、`OuterPosition` 两个命令时，AppKit 先按左上角不动改变大小、再移动，以鼠标为中心缩放时窗口会跳一下。
   找不到原生窗口（例如测试里）时仍然发视口命令。
3. **连续缩放时以自己设置的位置为准**（`PinState::set_frame`，400 ms 内有效）：egui 报告的窗口位置要等窗口事件送回来才更新，
   连续缩放时可能还是上一步之前的位置，以它为准算出的新位置会来回跳。拖动贴图时清掉。

## 影响

- 主面板（唯一可以拖动边缘调整大小的窗口）在 macOS 上拖动边缘时，内容可能比之前多一点抖动。截屏遮罩不改变大小，不受影响。
- egui_kittest 的 `wgpu` 特性仍会打开 egui-wgpu 的默认特性，但只影响测试的构建。

## 复查方法

在 `PinState::ui` 里调用 `sync_window` 之前临时加上每帧自动缩放、记录帧间隔的代码，`--pin <图片>` 启动后看日志：
帧间隔应稳定在一次屏幕刷新（60 Hz 屏幕约 16.7 ms）左右，不应出现几百毫秒以上的间隔。
